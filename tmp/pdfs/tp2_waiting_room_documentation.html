Waiting Room App - TP2 Page 1
Architecture generale Vue d'ensemble

Fonctionnement global

L'application represente une salle d'attente locale. L'utilisateur saisit le nom d'un client, clique sur le bouton Add, puis le client apparait dans la liste. Chaque client affiche aussi une icone de suppression pour sortir de la file.

1. Saisie Le nom est entre dans le widget TextField.
2. Action Le bouton ElevatedButton appelle la methode _addClient().
3. Logique WaitingRoomManager ajoute ou supprime un nom dans la liste.
4. Affichage setState() reconstruit l'interface et met a jour le compteur.

Responsabilite de la logique

  • Stocker la liste des clients en memoire.
  • Ajouter un client avec addClient.
  • Supprimer un client avec removeClient.
  • Exposer la liste avec le getter clients.

Responsabilite de l'interface

  • Afficher le champ de saisie, le bouton, le compteur et la liste.
  • Lire le texte saisi avec TextEditingController.
  • Mettre a jour l'ecran avec setState().
  • Afficher un bouton de suppression pour chaque client.

Choix technique important

Le projet utilise une liste locale List<String>. Cela suffit pour ce TP, car l'objectif est de comprendre la gestion d'etat locale, les tests et le CI. Il n'y a pas de base de donnees ni d'appel reseau : les donnees existent seulement pendant l'execution de l'application.

Element Role Pourquoi c'est important
WaitingRoomManager Gere la liste des clients. Permet de tester la logique sans lancer l'interface Flutter.
WaitingRoomScreen Affiche et modifie la salle d'attente. Relie les actions utilisateur aux methodes du manager.
Tests Verifient l'ajout, la suppression et l'affichage. Reduisent le risque de regression.
Waiting Room App - TP2 Page 2
lib/waiting_room_manager.dart Logique metier

Gestionnaire de salle d'attente

Le fichier waiting_room_manager.dart contient la classe responsable de la liste des clients. Cette classe est volontairement simple : elle ne depend pas de Flutter, donc elle peut etre testee avec des tests unitaires rapides. 

class WaitingRoomManager {
  final List<String> _clients = [];

  List<String> get clients => _clients;

  void addClient(String name) {
    _clients.add(name);
  }

  void removeClient(String name) {
    _clients.remove(name);
  }
}

Attribut prive

_clients est une liste privee. Le caractere _ indique que cette variable est interne au fichier en Dart.

Getter public

clients permet a l'interface et aux tests de lire la liste actuelle pour afficher les noms et compter les elements.

Methode Action Exemple dans le projet
addClient(String name) Ajoute le nom a la fin de la liste. Utilisee quand l'utilisateur clique sur Add.
removeClient(String name) Supprime le premier element correspondant au nom. Utilisee quand l'utilisateur clique sur l'icone de suppression.

Point important : cette classe represente le coeur logique du TP. En la separant de l'interface, on peut valider le comportement de la file d'attente sans tester les widgets graphiques.

Limite volontaire du TP

Le getter retourne directement la liste interne. Pour un projet plus avance, on pourrait retourner une copie non modifiable afin d'eviter qu'un autre fichier modifie la liste sans passer par les methodes du manager. Pour ce TP, la version actuelle reste lisible et suffisante.

lib/main.dart Interface Flutter

Application et ecran principal

Le fichier main.dart lance l'application et construit l'interface. Il contient WaitingRoomApp, qui configure le MaterialApp, puis WaitingRoomScreen, qui gere l'ecran interactif. 

void main() {
  runApp(const WaitingRoomApp());
}

class WaitingRoomApp extends StatelessWidget {
  const WaitingRoomApp({super.key});

  @override
  Widget build(BuildContext context) {
    return MaterialApp(home: WaitingRoomScreen());
  }
}

Pourquoi un StatefulWidget ?

La liste des clients change pendant l'execution. L'ecran doit donc garder un etat local : le manager, le texte saisi et la liste affichee.

Role de setState()

Quand un client est ajoute ou supprime, setState() indique a Flutter de reconstruire l'interface pour montrer la nouvelle liste.

Ajout d'un client

void _addClient() {
  if (_controller.text.isNotEmpty) {
    setState(() {
      _manager.addClient(_controller.text);
      _controller.clear();
    });
  }
}

Cette methode evite d'ajouter un nom vide, transmet le texte au manager, puis vide le champ de saisie. Le compteur Clients in Queue: ... est mis a jour car l'interface est reconstruite.

Widget Fonction dans l'ecran
TextField Permet de saisir le nom du client.
ElevatedButton Declenche l'ajout du client.
Text Affiche le nombre de clients dans la file.
ListView.builder Construit dynamiquement une carte pour chaque client.
IconButton Supprime le client associe a la ligne.

test/waiting_room_manager_test.dart Tests unitaires

Validation de la logique metier

Les tests unitaires verifient directement WaitingRoomManager. Ils ne lancent pas l'interface graphique : ils testent seulement le comportement attendu de la liste.

Test d'ajout

  • Creer un manager vide.
  • Ajouter John Doe.
  • Verifier que la liste contient 1 client.
  • Verifier que le premier client est John Doe.

Test de suppression

  • Creer un manager.
  • Ajouter John Doe puis Jane Doe.
  • Supprimer John Doe.
  • Verifier qu'il reste seulement Jane Doe.
test('should add a client to the waiting list', () {
  final manager = WaitingRoomManager();
  manager.addClient('John Doe');

  expect(manager.clients.length, 1);
  expect(manager.clients.first, 'John Doe');
});

Methode Arrange - Act - Assert

Etape Explication Exemple
Arrange Preparer les donnees du test. Creer WaitingRoomManager.
Act Executer l'action a tester. Appeler addClient ou removeClient.
Assert Verifier le resultat obtenu. Utiliser expect(...).

Ces tests prouvent que la couche logique fonctionne seule. Si un probleme apparait dans l'interface, on sait que le manager a deja une base verifiee.

test/waiting_room_widget_test.dart Tests widgets

Validation de l'interface utilisateur

Les tests widgets verifient l'application comme un utilisateur : ils demarrent le widget, simulent une saisie, cliquent sur les boutons et inspectent ce qui est affiche a l'ecran.

pumpWidget

Construit l'application dans l'environnement de test.

enterText

Simule la saisie d'un nom dans le champ texte.

tap + pump

Simule le clic puis force la reconstruction de l'interface.

Scenario 1 : ajouter Alice

await tester.pumpWidget(const WaitingRoomApp());
await tester.enterText(find.byType(TextField), 'Alice');
await tester.tap(find.byType(ElevatedButton));
await tester.pump();

expect(find.text('Alice'), findsOneWidget);
expect(find.text('Clients in Queue: 1'), findsOneWidget);

Scenario 2 : supprimer Bob

Le test ajoute d'abord Bob, clique sur l'icone Icons.delete, puis verifie que le nom n'existe plus dans l'ecran et que le compteur revient a zero.

Verification Resultat attendu
find.text('Alice') Un seul widget affiche le nom apres l'ajout.
find.text('Clients in Queue: 1') Le compteur augmente apres l'ajout.
find.text('Bob') Aucun widget ne contient Bob apres suppression.
find.text('Clients in Queue: 0') Le compteur revient a zero apres suppression.

Note : le projet contient aussi test/waiting_room_card_test.dart, qui verifie l'affichage du composant WaitingRoomCard. Ce test complete la couverture globale du projet.

.github/workflows/ci.yml Integration continue

Pipeline GitHub Actions

Le fichier ci.yml automatise la verification du projet a chaque modification envoyee sur la branche main, ou lors d'une pull request vers main. 

on:
  pull_request:
    branches: [ main ]
  push:
    branches: [ main ]

steps:
  - uses: actions/checkout@v4
  - uses: subosito/flutter-action@v2
    with:
      flutter-version: '3.47.4'
  - run: flutter pub get
  - run: flutter test
  - run: flutter analyze

Ce que le CI controle

  • Recuperation du code avec checkout.
  • Installation de Flutter version 3.47.4.
  • Installation des dependances du projet.
  • Execution de tous les tests automatises.
  • Analyse statique du code Dart.

Resultats verifies localement

flutter test : tous les tests passent

flutter analyze : aucun probleme trouve
